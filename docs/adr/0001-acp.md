# ADR 0001 · Agent Client Protocol (ACP) support

- **Status:** Proposed (merge with the go/no-go below)
- **Date:** 2026-10-29
- **Story:** E6-S5 (spike). Follow-up: E6-S6.
- **Decision drivers:** let flows use agents we do not build (Claude Code, Codex, Gemini CLI) as steps; let editors that speak ACP (Zed, JetBrains) run our flows.

## Recommendation

| Direction | Recommendation |
|---|---|
| **(1) Host external ACP agents as flow steps** | **GO.** The prototype in this branch runs a flow whose first step is an external ACP agent; its final message reaches the next step as `{input:<id>}`. The protocol fits our flow model with little glue. Build it out in E6-S6. |
| **(2) Expose our flows to ACP editors** | **NO-GO for now, revisit after E6-S6.** It needs an agent-side server mode (a second protocol surface), a mapping of flows onto ACP sessions and a story for approvals through the editor. Nobody has asked for it yet, and (1) teaches us the protocol first. |

## Protocol summary

ACP is an open protocol (Apache-2.0) between a **client** (an editor or, here, VCH) and an **agent** (a coding agent run as a subprocess). Transport is JSON-RPC 2.0 over the agent's stdio, one JSON object per line. Both sides send requests and notifications.

**Version.** The protocol version is a single integer that only changes for breaking changes; the client sends the highest it supports and the agent answers with the one it picked. The agents that ship today (Gemini CLI, the Claude Code and Codex adapters, Copilot CLI, Goose and others) implement **version 1**. The specification site also documents a **version 2** with a restructured `initialize` (`capabilities`/`info` instead of `clientCapabilities`/`clientInfo`, session capabilities under `capabilities.session`, optional `auth/login`). The prototype speaks v1 and refuses anything else with a clear message. Which agents have moved to v2 must be re-checked when E6-S6 starts (open question 1).

**Baseline calls used by the prototype (v1)**

| Direction | Method | Purpose |
|---|---|---|
| client → agent | `initialize` | version and capabilities (we offer `fs.readTextFile`, `fs.writeTextFile`; no terminal yet) |
| client → agent | `session/new` | `{cwd, mcpServers}` → `{sessionId}` |
| client → agent | `session/prompt` | `{sessionId, prompt:[{type:"text", text}]}` → `{stopReason}` when the turn ends |
| client → agent | `session/cancel` (notification) | stop the running turn; the pending `session/prompt` then ends with `stopReason: "cancelled"` |
| agent → client | `session/update` (notification) | `agent_message_chunk`, `tool_call`, `tool_call_update`, `plan`, ... |
| agent → client | `session/request_permission` | `{toolCall, options[]}` → `{outcome: selected(optionId) \| cancelled}`; option kinds `allow_once`, `allow_always`, `reject_once`, `reject_always` |
| agent → client | `fs/read_text_file`, `fs/write_text_file` | file access through the client |
| agent → client | `terminal/*` | run commands through the client (not used yet) |

Stop reasons: `end_turn`, `max_tokens`, `max_turn_requests`, `refusal`, `cancelled`. Tool call kinds: `read`, `edit`, `delete`, `move`, `search`, `execute`, `think`, `fetch`, `switch_mode`, `other`.

## Mapping onto VCH

### Hosting an external agent (direction 1)

| ACP | VCH |
|---|---|
| a subprocess + `initialize` + `session/new` | one **flow step** of `kind: "acp"` (`acpCommand`, `acpArgs`); one ACP session per step run, like one orchestrator session per node (`{flow}/{node}#{iteration}`) |
| `session/prompt` text | `FlowPrompt.Build(...)`: the step's template with `{task}` and `{input:id}` filled in, exactly as for built-in agents |
| `agent_message_chunk` stream | the step's output text. The prototype uses **the text after the last tool call**, or everything when the agent says nothing after it, so narration like "let me look at the files" does not leak into the next step |
| `stopReason` | `end_turn` → done; `cancelled` → cancelled node; `refusal` → failed node; anything else → done if there is text |
| `OUTCOME: x` convention | works unchanged: the text is parsed with `FlowPrompt.ParseOutcome`, so conditional edges and review loops work with external agents. (A follow-up "state only your outcome" prompt on the same session is not in the prototype.) |
| `tool_call` | progress line in the run (`StatusUpdateEvent`) and a tool-call count in the run record. E6-S6: map `tool_call_update` content to `ToolCallEndEvent` and diffs to `DiffProducedEvent` so the timeline and the report (E5-S8) show them |
| `session/request_permission` | the **VCH approval model**. Prototype: decided from the flow's `PermissionMode` by `AcpPermissionPolicy` (read-only kinds always; `edit` needs AutoEdit or FullAuto; everything else needs FullAuto; refusals answer with a `reject_once` option; "always" options are used only in FullAuto). E6-S6: raise an `ApprovalRequestEvent` per request (the same card flows use for risky tools) and reply with the user's choice |
| `fs/read_text_file` | allowed inside the working directory only (path confinement) |
| `fs/write_text_file` | refused unless the mode allows edits; inside the working directory only |
| `session/cancel` | sent when the flow is cancelled or the step times out (`FlowRunOptions.ConfirmationTimeout` is reused as the step timeout in the prototype) |
| agent token usage | not reported by ACP v1 (some agents add it under `_meta`); the report shows tokens as unknown for ACP steps, cost as $0, and the flow budget cap cannot stop an external agent (see risks) |

`IAiProvider` is **not** the right seam. It models "complete a chat request with tools", where VCH owns the loop and the tools. An ACP agent owns its loop and its tools, and VCH is the host. So the integration sits next to `IAgentOrchestrator` at the flow-step level (`IExternalAgentRunner`), not inside the provider abstraction. Forcing an ACP agent behind `IAiProvider` would hide its tool calls and permission requests, which are the two things we need to govern.

### Exposing flows to editors (direction 2, for later)

| ACP (we are the agent) | VCH |
|---|---|
| `session/new` | a flow run context; the `cwd` becomes the working directory |
| `session/prompt` | `task` for a chosen flow (flow picked by a mode/config option, default configurable) |
| `session/update` | `FlowNodeStatusEvent` → `plan` entries; node output → `agent_message_chunk`; tool calls → `tool_call` |
| `session/request_permission` (we send it) | our `ApprovalRequestEvent`, answered by the editor's UI |
| `fs/*` from the editor | needed so unsaved editor buffers are visible; our file tools would have to call back to the client |

This needs a server mode (`aiagent acp`), a re-entrant mapping of parallel flow nodes onto one session, and file tools that can read through the client. Roughly a second epic; deferred.

## Prototype (this branch)

- `Core/Flows/IExternalAgentRunner.cs`: the seam (request, result, exception).
- `SdlcStageDefinition`: `kind: "acp"`, `acpCommand`, `acpArgs`. `FlowGraph` validates them (command required; character/model/provider ignored with a warning).
- `FlowRunner.StartAcpNode`: builds the prompt, calls the runner, returns the final message as the node output, supports outcomes, cancellation and failures.
- `Tools/Acp/AcpConnection.cs`: JSON-RPC over NDJSON (requests both ways, notifications, error mapping, EOF handling).
- `Tools/Acp/AcpAgentRunner.cs`: initialize → session/new → session/prompt, permission and `fs/*` handling, cancel, timeout, stderr tail in errors, Windows `.cmd` launch through the same resolver as MCP.
- Registered in the app and the CLI. No UI yet.
- Example step:
  ```json
  { "id": "external-review", "kind": "acp", "acpCommand": "gemini", "acpArgs": ["--acp"],
    "promptTemplate": "Review this task: {task}" }
  ```
- Tests: `AcpAgentRunnerTests` (scripted in-memory agent: text selection, permission modes, fs confinement, version and auth errors, crash, cancel, timeout), `AcpStepTests` (flow: `{input:external-review}` reaches the next step; outcomes; missing runner; failure stops the branch).
- **Real-agent smoke test:** `RealAgent_AnswersAPrompt` runs when `VCH_ACP_COMMAND` is set, for example `VCH_ACP_COMMAND=gemini VCH_ACP_ARGS=--acp dotnet test --filter RealAgent`. It was **not run** while writing this ADR (no agent CLI and no network access in the authoring environment), so compatibility with the real agents is untested. Run it once per agent before relying on this.

## Risks

1. **Licensing.** The protocol and the reference SDKs are Apache-2.0. The agents are separate products: using Claude Code, Codex or Gemini CLI as a step means the user's own installation and account, under that vendor's terms. We must not bundle or redistribute them, and we must not pass one user's credentials around. Check each vendor's terms on automated or programmatic use of subscription logins before we document a setup (open question 2).
2. **Authentication.** ACP agents sign in themselves (login command, API key in their own environment, or a subscription). The `initialize` response can list `authMethods`; v1 has an `authenticate` call for it. The prototype only maps the "auth required" error to a message ("sign in first"). E6-S6 should show the agent's auth methods and, for terminal-based logins, open a terminal. Secrets must stay in the agent's environment; the step definition must never hold tokens (same rule as MCP, E6-S3).
3. **Sandboxing and permissions.** An external agent can run commands and edit files on its own. We only control what it asks the client to do (`fs/*`, `terminal/*`, `session/request_permission`); an agent can also act directly in its own process. Mitigations: run the step in a **git worktree** like built-in parallel steps (not in the prototype; it runs in the working directory), start it with its own read-only/plan mode where it has one, keep our permission answers conservative, show every permission and tool call in the run record, and document that "plan" mode on our side does not make the external agent read-only unless the agent honours it.
4. **Budget and cost.** ACP v1 has no standard usage reporting, so `MaxBudgetUsd` cannot stop an ACP step. The flow can only check the budget before the step starts, and time out the step.
5. **Protocol churn.** v1 is the shipping version; v2 changes `initialize` and capability shapes. Isolate the wire format in `AcpConnection` and one `AcpAgentRunner`, add a v2 variant behind the same `IExternalAgentRunner`, and negotiate: offer the highest version we implement.
6. **Output quality.** "Final message = text after the last tool call" is a heuristic. Agents that stream a summary before their last tool call lose it. Mitigation: let the step template ask for a clearly marked final answer (for example "end with `RESULT:`") and prefer it when present.
7. **Windows.** Agents installed with npm are `.cmd` shims; the launcher resolves them (as for MCP). Long command lines and quoting need a test on Windows with each agent.
8. **Hangs.** An agent can stall without closing its pipes. A per-step timeout exists (reuses the confirmation timeout in the prototype; give it its own setting in E6-S6) and the process is killed after a 2 s grace period.

## Open questions

1. Which of the target agents implement v1 and which v2 today, and do the Claude Code and Codex adapters still need a separate package or are built in? (The spec site and the third-party pages disagree on details; verify against each agent's current release.)
2. Terms of use for driving each vendor's agent from another tool with a subscription login.
3. Do we expose `terminal/*` (we would have to run and stream commands under our own sandbox), or leave it out so the agent uses its own shell? Leaving it out is simpler but gives us less control.

## Estimate for E6-S6 (hosting external agents, direction 1)

About **10 working days** (size L), in this order:

| Work | Days |
|---|---|
| Approval bridge: `session/request_permission` → `ApprovalRequestEvent` card, "remember for this step" rules, timeouts | 1.5 |
| Events and report: map `tool_call`/`tool_call_update`/`plan` to timeline events, diffs and the flow report; stream message chunks live | 2 |
| Worktree isolation and merge-back for ACP steps (reuse `RunIsolatedStepAsync` logic) | 1.5 |
| Agent profiles: settings list of agents (name, command, args, env references, auth), "Test" button like E6-S3, step `agent: <profile>` instead of raw command | 2 |
| Auth: show `authMethods`, terminal login helper, clear errors | 1 |
| `terminal/*` through our shell tool with sandbox rules (optional; cut if time is short) | 1.5 |
| Real-agent matrix (Gemini CLI, Claude Code adapter, Codex adapter) on Windows/macOS/Linux, v2 negotiation, docs | 1.5 |

Direction 2 (server mode) is a separate story of about 8 to 10 days and is not part of this estimate.
